## Лабораторная работа в «1С:Предприятие»

**Тема №20: «Контроль неснижаемого остатка товаров на складе»**  
**Исполнители:** два студента  
**Результат:** одна работающая учебная информационная база 1С, содержащая основную складскую задачу и четыре дополнительные задачи, выгруженная в **один файл `.dt`**.  
**Редакция:** финальная, после сверки с транскрипцией встречи и файлом заданий.

> **Статусы требований.** **[П]** — непосредственно следует из объяснения преподавателя в транскрипции; **[З]** — задано в файле с дополнительными заданиями; **[Р]** — рекомендуемое проектное решение, конкретная реализация которого преподавателем не предписана; **[У]** — обстоятельство, для которого в источниках нет однозначного указания. Статусы нужны, чтобы не принимать предложенную архитектуру за слова преподавателя.

## 1. Цель и состав работы

Разработать в Конфигураторе 1С прикладную конфигурацию, которая:

1. Ведёт учёт товаров на **нескольких складах** по приходным и расходным накладным. **[П]**
2. Хранит для каждого товара **неснижаемый (минимальный) остаток** и не допускает отпуск товара, после которого остаток на конкретном складе окажется ниже установленного минимума. **[П]**
3. Формирует отчёты о движении и остатках товаров по данным **регистров**, включая отчёты по поставщикам и получателям. **[П]**
4. Содержит необходимые справочники, формы с автоматизацией, печатную форму, смысловые подсистемы, импорт **или** экспорт данных и компонент анализа данных. **[П]**
5. Содержит четыре дополнительные вычислительные задачи: **№4, №12, №22 и №26**. Их нужно встроить в **эту же конфигурацию**. **[П, З]**

Для **двух студентов** преподаватель требует **четыре отчёта или больше**. Среди отчётов должны быть представлены **линейный, табличный и диаграмма**. **[П]**

## 3. Предметная область и справочники

### 3.1. Справочники

| Объект метаданных (предлагаемое имя) | Основные данные | Статус |
|---|---|---|
| `Товары` | Наименование; **МинимальныйОстаток**; при необходимости единица измерения | Наличие товара и его минимума — [П]; имена полей — [Р] |
| `Склады` | Код/наименование | Несколько складов — [П]; состав реквизитов — [Р] |
| `Поставщики` | Наименование; при необходимости контактные данные | Справочник поставщиков — [П] |
| `Получатели` или `Подразделения` | Наименование подразделения, которому выдаётся товар | Получатели/внутренние подразделения — [П] |

Преподаватель предложил хранить **минимальный остаток в справочнике товаров**. В базовом варианте один норматив товара применяется при проверке **каждого склада отдельно**. Индивидуальные минимумы по складам — возможное расширение, а не требование записи. **[П, Р]**

### 3.2. Документы

**`ПриходнаяНакладная`** **[П]**

- Шапка: дата, склад, поставщик. **[Р: рекомендуемый состав полей]**
- Табличная часть `Товары`: товар, количество. **[Р]**
- При проведении увеличивает количество товара на выбранном складе в регистре накопления. **[П, Р]**

**`РасходнаяНакладная`** **[П]**

- Шапка: дата, склад, получатель/подразделение. **[Р]**
- Табличная часть `Товары`: товар, количество. **[Р]**
- Перед записью и проведением проверяет достаточность остатка с учётом неснижаемого минимума. **[П]**
- Только при успешной проверке формирует расходные движения. **[П]**

**Рекомендуемые проверки ввода [Р]:** обязательные реквизиты заполнены; количество каждой строки больше нуля; один товар, присутствующий в нескольких строках одного документа, проверяется по **общей сумме**; при отказе не возникает частичного списания.

### 3.3. Договоры: не путать с основным заданием

В первоначальном обсуждении группы упоминалось оформление договоров. Однако в **транскрипции описания именно складской темы** преподаватель перечисляет **приходную и расходную накладные** и **не задаёт** отдельный механизм договоров или резервирования. **[У]**

- **Обязательная реализация по подтверждённому объяснению:** приходная и расходная накладные с проверкой неснижаемого остатка. **[П]**
- **Дополнение по желанию группы:** документ `ДоговорОтпуска` с реквизитами склада, получателя и товаров. **[Р]**
- Если вводится договор, нельзя дважды списать один и тот же товар: и договором, и расходной накладной. Резервирование по договорам потребует отдельного проектирования и в транскрипции не описано. **[Р]**

**Вывод:** договоры **не должны задерживать разработку и проверку обязательной части**, пока их обязательность не подтверждена отдельным заданием преподавателя.

## 4. Регистры и источники данных

### 4.1. Основной регистр накопления

**`ОстаткиТоваров`**, вид регистра — **«Остатки»**. **[Р: техническая схема, соответствующая описанию преподавателя]**

- Измерения: `Склад`, `Товар`.
- Ресурс: `Количество`.
- Регистраторы: приходная и расходная накладные.
- Приходная накладная формирует движения **«Приход»**, расходная — **«Расход»**.
- По данным регистра рассчитываются начальные остатки, приход, расход и конечные остатки.

**Важно:** поставщика и получателя не следует добавлять в измерения основного **регистра остатков**, если это разделит один реальный остаток товара на несколько фиктивных остатков по контрагентам. **[Р]**

### 4.2. Аналитика для отчётов

Чтобы строить отчёты **по поставщикам** и **по получателям** и не читать данные напрямую из документов, рекомендуется добавить: **[Р]**

| Регистр | Вид | Измерения | Ресурс | Источник движений |
|---|---|---|---|---|
| `ПоступленияПоПоставщикам` | Накопления, обороты | Склад, Товар, Поставщик | Количество | Приходная накладная |
| `ВыдачиПоПолучателям` | Накопления, обороты | Склад, Товар, Получатель | Количество | Расходная накладная |

Имена и количество вспомогательных регистров **не установлены преподавателем**. Его обязательное правило: **отчёты строить по регистрам, а не непосредственно по документам**. **[П]**

**Регистр сведений:** преподаватель объяснял его назначение на примерах истории цен и окладов, но не установил отдельный складской сценарий для обязательного использования. Поэтому вводить его «для галочки» не требуется, если не появится обоснованная потребность; начало транскрипции обрывается на фразе о видах регистров, так что это не следует считать категорическим запретом или разрешением. **[У, Р]**

## 5. Ключевая бизнес-логика: контроль неснижаемого остатка

### 5.1. Правило

Проверка проводится **отдельно по каждому товару и выбранному складу**. **[П]**

```text
ОстатокПосле = ОстатокДо − КоличествоКОтпуску

Если ОстатокПосле >= МинимальныйОстаток:
    расход допустим
Иначе:
    показать предупреждение;
    отказать в записи и проведении документа;
    не создавать расходных движений.
```

Значение `ОстатокДо` берётся из **регистра складских остатков**, а `МинимальныйОстаток` — из справочника товаров. **[П, Р]**

**Граница допустимости:** если после выдачи осталось **ровно столько, сколько установлено минимумом**, расход разрешён. Если осталось хотя бы меньше — запрещён. **[П]**

### 5.2. Что должно происходить в форме и при записи

1. Пользователь выбирает склад и получателя, добавляет товар и количество.
2. Конфигурация получает остаток **этого товара на этом складе** из регистра. **[П, Р]**
3. Определяет неснижаемый минимум и ожидаемый остаток после операции. **[Р]**
4. При попытке записать или провести недопустимый документ выдаёт понятное сообщение, например: `Склад 1, Кирпич: остаток 10 000, отпуск 9 001, минимум 1 000; после отпуска 999. Запись/проведение запрещены.` **[П, Р]**
5. При отказе товар в регистре не уменьшается, данные по другим строкам этого документа тоже не списываются. **[П, Р]**

**Рекомендация для разработки в 1С [Р]:** предусмотреть контроль на уровне объекта при записи и повторную защиту при проведении, а не полагаться только на визуальное предупреждение формы. Это необходимо, чтобы запрет работал независимо от способа вызова операции. Точные обработчики и способ отмены выбираются при реализации с учётом версии учебной платформы.

### 5.3. Примеры преподавателя

| Склад / товар | Исходный остаток | Минимум | Расход | Остаток после | Решение |
|---|---:|---:|---:|---:|---|
| Склад 1 / кирпич | 10 000 | 1 000 | 9 000 | 1 000 | **Разрешить** |
| Склад 1 / кирпич | 10 000 | 1 000 | 9 001 | 999 | **Запретить запись и проведение** |
| Склад 2 / кирпич | 2 500 | 1 000 | 1 500 | 1 000 | **Разрешить**; остаток склада 1 не используется |
| Склад 2 / кирпич | 2 500 | 1 000 | 1 501 | 999 | **Запретить** |

Числа в первых двух строках основаны на примере преподавателя; пример второго склада конкретизирован для тестирования. **[П, Р]**

## 6. Формы, автоматизация, реквизиты и печать

Преподаватель требует, чтобы формы **не были простым ручным вводом**: в них должны быть **автозаполнение/авторасчёт**, а также **программное изменение реквизитов**. Если в табличной части есть суммируемые показатели, должен считаться итог. **[П]**

### Рекомендуемая конкретная реализация [Р]

1. **Автозаполнение по данным регистров:** при выборе склада и товара в расходной накладной автоматически выводить остаток товара, неснижаемый минимум и **доступное количество к отпуску** (`Макс(0, Остаток − Минимум)`).
2. **Авторасчёт:** при изменении количества автоматически пересчитывать `ОстатокПосле`; внизу табличной части выводить **итого количество**.
3. **Программное изменение реквизита:** например, автоматически устанавливать реквизит формы `ДоступноКОтпуску` или `ОстатокПосле` при изменении склада, товара или количества; продемонстрировать работающий обработчик формы.
4. **Осмысленное заполнение:** при подборе товара из справочника заполнять зависимые реквизиты без повторного ввода вручную. Отдельная кнопка «Заполнить» возможна, но сам факт наличия кнопки без полезного действия не удовлетворяет смыслу требования.
5. **Печатная форма:** создать макет печати хотя бы одной накладной и команду **«Печать»**. Рекомендуется печать обеих накладных, но требование печатных форм не задаёт в транскрипции точного количества.

В Конфигураторе обработчики формы могут использовать клиентские и серверные процедуры; преподаватель показал этот принцип на демонстрационной кадровой конфигурации. Реализовывать кадровые документы по фотографии **не нужно**. **[П]**

## 7. Отчёты: минимум четыре для двух студентов

**Общие правила [П]:** отчётные показатели получают **из регистров**; должны присутствовать **линейный**, **табличный** отчёты и **диаграмма**. Выбор конкретных четырёх отчётов ниже — проектное решение, основанное на том, что преподаватель назвал при описании складской темы. **[Р]**

| № | Название | Вид | Показатели и настройки | Основной источник |
|---|---|---|---|---|
| **1** | **Контроль неснижаемого остатка** | **Табличный** | Выбор склада и периода; товар, остаток на начало, приход, расход, остаток на конец, минимум, дельта | `ОстаткиТоваров` |
| **2** | **Поступления от поставщиков** | **Линейный** | Период, склад, поставщик; товары и количество поступления, итог | `ПоступленияПоПоставщикам` |
| **3** | **Выдача получателям** | **Линейный** | Период, склад, подразделение; товары и количество выдачи, итог | `ВыдачиПоПолучателям` |
| **4** | **Диаграмма движения товаров** | **Диаграмма** | Например, столбцы прихода и расхода по товарам за период с фильтром склада | Регистры накопления |

### 7.1. Основной табличный отчёт

Преподаватель предложил **сначала выбрать склад**, а затем вывести товары и показатели примерно следующего вида:

| Товар | Остаток на начало | Пришло | Ушло | Остаток на конец | Неснижаемый остаток | Дельта |
|---|---:|---:|---:|---:|---:|---:|
| Кирпич | 10 000 | 0 | 9 000 | 1 000 | 1 000 | 0 |

**Дельта = Остаток на конец − Неснижаемый остаток.** Название «Остаток на начало» использовано как однозначный вариант устно сказанного «текущий остаток» при наличии периода; это проектное уточнение. **[Р]**

Для контроля удобен вывод товаров с дельтой **0** и **больше 0**; отрицательная дельта должна выявлять проблемное состояние, если оно возникло из-за изменения норматива или исходных данных. **[Р]**

### 8.1. Задание №4 — гипотенуза

**Точная формулировка [З]:** «Вычислить длину гипотенузы по заданным значениям катетов».

- Ввод: катеты `a`, `b`; вывод: гипотенуза `c`. **[Р]**
- Формула: **`c = √(a² + b²)`**.
- Для геометрического случая принимать **`a > 0`, `b > 0`**; при ошибке показывать понятное сообщение. **[Р]**
- Проверка: `a = 3`, `b = 4` → **`c = 5`**.

### 8.2. Задание №12 — корень из суммы квадратов

**Точная формулировка [З]:** «Разработать процедуру, рассчитывающую корень из суммы квадратов двух введённых чисел».

- Ввод: `x`, `y`; вывод: `r`. **[Р]**
- Формула: **`r = √(x² + y²)`**.
- Нужно реализовать **отдельную процедуру**, поскольку это прямо сказано в условии. **[З]**
- В отличие от катетов, числа могут быть отрицательными. **[Р]**
- Проверка: `x = 6`, `y = 8` → **`r = 10`**.

**Важно:** формулы №4 и №12 совпадают, но обе задачи **должны быть представлены отдельно** в интерфейсе; №12 дополнительно демонстрирует вызов процедуры. **[З, Р]**

### 8.3. Задание №22 — плата за водоснабжение

**Точная формулировка [З]:** «По заданным начальному и конечному показаниям водосчётчика и тарифу за 1 м³ рассчитать величину оплаты за водоснабжение».

- Ввод: начальное показание `N0`, конечное показание `N1`, тариф `T` за 1 м³. **[Р]**
- Расход воды: **`Q = N1 − N0`**.
- Оплата: **`S = Q × T`**.
- Проверка: `N1 ≥ N0`, `T ≥ 0`; сброс или переполнение счётчика в условии не описаны. **[Р]**
- Пример: `N0 = 120`, `N1 = 135`, `T = 40` → `Q = 15 м³`, **`S = 600`**.

### 8.4. Задание №26 — начисление оплаты труда

**Точная формулировка [З]:** «По заданной ставке оплаты труда за 1 час, количеству отработанных часов вычислить НДФЛ, сумму профсоюзных взносов по ставке 1% и сумму к выдаче».

**Вход:** почасовая ставка `P`; количество часов `H`; **ставка НДФЛ `R` в процентах** как явно задаваемый учебный параметр. **[Р]**

| Показатель | Формула для учебной модели |
|---|---|
| Начислено (`G`) | `P × H` |
| НДФЛ (`N`) | `G × R / 100` |
| Профсоюзные взносы (`U`) | `G × 0,01` |
| К выдаче (`K`) | `G − N − U` |

Проверить `P ≥ 0`, `H ≥ 0`, `0 ≤ R ≤ 100`; денежные результаты показывать с точностью до двух знаков. **[Р]**

**Тест с условной, а не предписанной ставкой НДФЛ:** `P = 500`, `H = 160`, `R = 13%` → начислено **80 000**; НДФЛ **10 400**; профсоюзные взносы **800**; к выдаче **68 800**.

> **В исходном условии задачи №26 ставка НДФЛ не указана.** Значение **13% не является требованием преподавателя** и не выдаётся за универсальную налоговую ставку. Это исключительно тестовое значение входного параметра. Правила вычетов и прогрессивных ставок в задании также не описаны. **[У]**

### 8.5. Общие критерии готовности задач

- Четыре **разных** пункта меню и четыре открывающиеся формы. **[П, Р]**
- На каждой форме: поля ввода, команда **«Рассчитать»**, результат. **[Р]**
- Расчёт выполняется средствами языка 1С, не вручную и не в Excel. **[П, Р]**
- Повторный расчёт обновляет результат; недопустимые значения обрабатываются сообщением. **[Р]**
- Все задачи входят в единую информационную базу и, следовательно, в один `.dt`. **[П]**

## 10. Обмен данными, анализ данных и сдача

### 10.1. Импорт или экспорт

**Обязательно выполнить хотя бы одно направление:** **импорт** либо **экспорт** в Excel, DBF или иной подобный формат. **[П]**

### 10.2. Компонент «Анализ данных»

Преподаватель прямо говорит, что **анализ данных — завершающий этап**, который группа должна встроить в конфигурацию, **ориентируясь на образец**, предоставляемый преподавателем ближе к зачёту. **[П]**

- В ТЗ **сохраняется обязательность интеграции**. **[П]**
- **Точная форма компонента и алгоритм его подключения неизвестны из транскрипции**. Изобретать обязательный конкретный механизм анализа данных нельзя. **[У]**
- После получения образца можно применить анализ к складским показателям: приходу, расходу, остаткам и отклонениям от минимального уровня. **[Р]**

### 10.3. Передача результата

**Обязательно [П]:** из Конфигуратора выполнить **«Администрирование → Выгрузить информационную базу»** и передать **один файл формата `.dt`**, в который входят:

В записи преподаватель просил передать файл **через MAX**. **[П]** Практическая рекомендация: перед отправкой проверить восстановление выгрузки на чистой учебной базе, но это **не отдельное требование преподавателя**. **[Р]**

## 11. Проверка готовности (приёмочные сценарии)

| Проверка | Действие | Ожидаемый результат |
|---|---|---|
| **1. Приход** | На склад 1 поступило 10 000 кирпичей, минимум 1 000 | Регистр показывает остаток 10 000 |
| **2. Допустимый расход** | Из исходных 10 000 отпустить 9 000 | Документ записывается и проводится; в остатке 1 000 |
| **3. Недопустимый расход** | **На исходном остатке 10 000**, в отдельном сценарии попытаться отпустить 9 001 | Предупреждение; **запись и проведение отклонены**; остаток остаётся 10 000 |
| **4. Разные склады** | При одинаковом товаре установить разные фактические остатки на складах 1 и 2 | Расход по одному складу не использует остаток другого |
| **5. Повтор товара** | В расходном документе указать один товар дважды, так что общий расход нарушает минимум | Система проверяет **сумму** количества и отклоняет документ целиком |
| **6. Автоматизация** | Выбрать товар/склад, изменить количество | Данные регистра подставляются, расчётный остаток и итог обновляются автоматически |
| **7. Отчётность** | Сформировать все четыре отчёта | Есть табличный, линейные и диаграмма; цифры основаны на регистрах |
| **8. Печать** | Нажать «Печать» в накладной | Получена корректная печатная форма |
| **9. Обмен** | Экспортировать или импортировать данные | Получен читаемый файл либо корректно загружены данные |
| **10. Задача №4** | `3`, `4` | Результат `5` |
| **11. Задача №12** | `6`, `8` | Результат `10`; в модуле есть процедура |
| **12. Задача №22** | `120`, `135`, тариф `40` | Расход `15 м³`, плата `600` |
| **13. Задача №26** | Ставка `500`, часы `160`, учебный НДФЛ `13%` | Начислено `80 000`, НДФЛ `10 400`, взносы `800`, к выдаче `68 800` |
| **14. Анализ данных** | Открыть интегрированный компонент | Показывает работу с данными конфигурации по образцу преподавателя |
| **15. Итоговая выгрузка** | Выгрузить базу и проверить содержимое | **Один `.dt`** включает основную тему и все четыре задачи |

**Примечание:** сценарии 2 и 3 нужно проводить от **одинакового исходного остатка** (отдельные тестовые состояния или отмена предыдущего проведения), иначе проверка чисел будет некорректной. **[Р]**

## 12. Рекомендуемая последовательность разработки

Это **план реализации [Р]**, а не утверждённый преподавателем порядок действий.

1. Создать учебную базу, конфигурацию и подсистемы.
2. Создать четыре справочника, ввести минимум товара, подготовить **не менее двух** тестовых складов (для демонстрации удобно три).
3. Создать регистр `ОстаткиТоваров`, приходную накладную и проверить движения прихода.
4. Создать расходную накладную; реализовать проверку **до записи и проведения**; испытать границу минимума и разные склады.
5. Добавить необходимые оборотные регистры; создать четыре отчёта по регистрам.
6. Доработать формы: автоматическая подстановка данных, авторасчёт, программное изменение реквизитов, итоги табличной части; добавить печать.
7. Реализовать четыре обработки с задачами №4, №12, №22, №26 и проверить примеры.
8. Реализовать импорт либо экспорт.
9. После получения образца интегрировать компонент анализа данных.
10. Провести приёмочные тесты и выгрузить **один `.dt`**.
