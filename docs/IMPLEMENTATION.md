# Реализация темы №20: связь кода с объектами 1С

**Статус:** вторая итерация. Созданы исходные BSL-модули и **черновые XML-метаданные** (Configuration.xml, 4 справочника, 2 документа, 3 регистра, 2 общих модуля, 4 обработки и 4 подсистемы). **Загрузка XML в учебную 1С пока не проверялась.** Управляемые формы **четырех вычислительных обработок** добавлены (поля ввода, кнопка «Рассчитать», вызовы серверного расчета), но не проверены в платформе. Формы складских документов, печатные макеты и отчеты СКД не готовы. Не выдавать успешно прошедшие статические проверки за запуск 1С.

## 1. Объекты метаданных, которые должны быть созданы

Имена **должны совпадать с кодом**, иначе BSL ссылается на несуществующие объекты. Ниже техническая модель, соответствующая финальному ТЗ.

| Тип | Имя | Обязательные свойства |
|---|---|---|
| Справочник | `Товары` | наименование; `МинимальныйОстаток`: Число(15,3), неотрицательное |
| Справочник | `Склады` | код, наименование; минимум 2 тестовых склада |
| Справочник | `Поставщики` | код, наименование |
| Справочник | `Получатели` | код, наименование |
| Документ | `ПриходнаяНакладная` | `Склад` (СправочникСсылка.Склады), `Поставщик` (СправочникСсылка.Поставщики), `ИтогоКоличество` (Число(15,3)); проведение включено |
| Документ | `РасходнаяНакладная` | `Склад` (СправочникСсылка.Склады), `Получатель` (СправочникСсылка.Получатели), `ИтогоКоличество` (Число(15,3)); проведение включено |
| Табличная часть каждого документа | `Товары` | `Товар` (СправочникСсылка.Товары), `Количество` (Число(15,3)) |
| Регистр накопления (остатки) | `ОстаткиТоваров` | измерения: `Склад` (СправочникСсылка.Склады), `Товар` (СправочникСсылка.Товары); ресурс `Количество` Число(15,3); регистраторы: обе накладные |
| Регистр накопления (обороты) | `ПоступленияПоПоставщикам` | измерения: `Склад`, `Товар`, `Поставщик` с соответствующими ссылочными типами; ресурс `Количество` Число(15,3); регистратор: приходная накладная |
| Регистр накопления (обороты) | `ВыдачиПоПолучателям` | измерения: `Склад`, `Товар`, `Получатель` с соответствующими ссылочными типами; ресурс `Количество` Число(15,3); регистратор: расходная накладная |
| Общий модуль | `СкладскойУчетСервер` | Сервер = Да, Вызов сервера = Нет, Глобальный = Нет |
| Общий модуль | `СкладскиеОтчетыСервер` | Сервер = Да, Вызов сервера = Нет, Глобальный = Нет |
| Обработки | `Задача04Гипотенуза`, `Задача12СуммаКвадратов`, `Задача22Водоснабжение`, `Задача26ОплатаТруда` | отдельные формы с полями ввода, кнопкой «Рассчитать» и реквизитами вывода |
| Подсистемы | `Склад`, `СкладскиеОтчеты`, `ДополнительныеЗадачи`, `Сервис` | отдельные пункты меню по ТЗ |

**Связь документа с регистрами обязательна:** в свойствах каждого документа зарегистрировать указанные выше регистры движения. Регистраторы оборотных регистров не должны делить физический складской остаток по контрагентам.

## 2. Реализованная логика записи и проведения

- Приход: перед записью проверяет реквизиты и положительные количества, рассчитывает итог; при проведении пишет приход в `ОстаткиТоваров` и оборот в `ПоступленияПоПоставщикам`.
- Расход: перед **любой записью**, кроме отмены проведения, проверяет заполнение и минимум по суммарному количеству каждой номенклатуры. Если документ уже проведён, добавляет обратно его прежние расходные движения к расчётному остатку. Проверка не переносит товары между складами.
- Проведение расхода: создает движения, устанавливает `БлокироватьДляИзменения`, записывает их и заново проверяет **фактические остатки после записи**. При нехватке ставит `Отказ = Истина`; транзакция проведения должна откатить изменения.
- При ровно минимальном остатке расход разрешён. При отсутствии остатка товар считается имеющим нулевой остаток.
- В текущей учебной модели контроль основан на **текущих остатках**. Проведение документов задним числом и пересчёт исторических остатков пока не поддерживаются. Это отдельный технический риск.

**Требуется проверить в платформе:** поведение при перепроведении (с прежними расходами), отмене проведения, смене склада, конкурентном отпуске, отрицательном/нулевом минимуме. BSL CI не умеет проверять эти сценарии.

## 3. Четыре отчёта СКД и источники данных

В общем модуле `СкладскиеОтчетыСервер` созданы функции:

1. `КонтрольМинимальныхОстатков(НачалоПериода, КонецПериода, Склад)` — остатки и обороты, минимум и дельта.
2. `ПоступленияПоставщиков(...)` — обороты по поставщикам.
3. `ВыдачиПолучателям(...)` — обороты по получателям.
4. `ДанныеДиаграммыДвижений(...)` — данные прихода/расхода для диаграммы.

Все запросы читают **регистры**, а не документы. Также добавлены XML-объекты `Reports/` со схемами СКД: табличный контроль остатков, линейные отчёты по поставщикам и получателям и диаграмма движения товаров. По необходимости платформа автоматически строит стандартную форму отчёта по СКД. Поведение отчётов нужно проверить на рабочей учебной базе.

## 4. Дополнительные задания: заготовленные расчеты

| Задание | Обработка / экспортируемый метод | Тест |
|---|---|---|
| №4 гипотенуза | `Задача04Гипотенуза.Рассчитать(a, b)` | 3,4 → 5; значения должны быть > 0 |
| №12 корень суммы квадратов | `Задача12СуммаКвадратов.Рассчитать(x,y)` вызывает отдельную процедуру `РассчитатьКореньСуммыКвадратов` | 6,8 → 10; отрицательные допустимы |
| №22 плата за воду | `Задача22Водоснабжение.Рассчитать(N0,N1,T)` возвращает структуру | 120,135,40 → 15 м³ и 600 |

Ставка НДФЛ — входной учебный параметр, не законодательно фиксированная величина. Для каждой задачи теперь имеется отдельная **черновая управляемая форма** и пункт подсистемы; открытие форм и расчеты необходимо проверить в учебной 1С.

## 5. Что осталось для реальной сдачи

- Выполнить **реальную загрузку** в учебную платформу 1С через `scripts/check-config-in-onec.sh` и исправить выявленные платформой ошибки XML/модулей.
- Открыть интерфейс и убедиться, что формы документов, четыре обработки задач, четыре отчёта СКД, диаграмма и компонент `АнализДанных` действительно работают.
- Проверить команды **Печать** и **Экспорт в Excel**: в проекте реализовано программное построение табличного документа без статического макета `.mxl`. Если преподаватель требует именно макет в дереве конфигурации, его нужно создать дополнительно.
- Запустить сервис **Проверка лабораторной**. Он создаёт тестовые данные и проверяет часть приёмочных сценариев, но не заменяет ручную проверку интерфейса и форм.
- Сверить компонент анализа данных с примером преподавателя, который **не представлен** в исходных материалах. Нынешний вариант использует встроенный `АнализДанныхОбщаяСтатистика`.
- Создать конечную базу с демонстрационными данными, выгрузить через `scripts/dump-demo-dt.sh` и восстановить финальный `.dt`.

Операции `/LoadConfigFromFiles`, `/UpdateDBCfg`, `/CheckConfig` и `/DumpIB` нельзя заменить линтером BSL. См. [RUN_IN_ONEC.md](RUN_IN_ONEC.md).

## 6. Проверка текущего коммита

GitHub Actions запускает **BSL Language Server** и `scripts/check-metadata.py` для проверки структуры XML. Успешный CI означает только отсутствие ошибок BSL-парсера `ParseError` и найденных структурных несоответствий XML. Он **не проверяет** импорт, запуск формы, правильность выполнения запросов, права, работу макетов или состояние `.dt`.

Чтобы проверить настоящую платформу 1С, выполните [инструкцию](RUN_IN_ONEC.md).
