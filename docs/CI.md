# CI для учебной версии «1С:Предприятие» 8.3

## Что проверяется

1. **На стандартном GitHub Runner (автоматически)**: `nix flake check` проверяет скрипты через `shellcheck` и `shfmt`, YAML GitHub Actions через `actionlint`, запускает тесты обвязки проверки `.dt` и убеждается, что итоговое ТЗ присутствует. Это **не** проверка базы данных.
2. **На отдельном Linux x86_64 Runner (после включения)**: установленный *официальный учебный* исполняемый файл **`1cv8t`** загружает `artifacts/warehouse.dt` в одноразовую файловую базу через `/RestoreIB`, проверяет конфигурацию через `/CheckConfig`, проверяет целостность базы через `/IBCheckAndRepair ... -TestOnly` и выгружает конфигурацию через `/DumpCfg`. Ошибка любого этапа ломает job.

> Важно: успешное восстановление и статические проверки не доказывают правильность расчёта неснижаемого остатка, корректность всех отчётов и выполнение четырёх дополнительных задач. Эти сценарии нужно проверять отдельно в самой 1С.

## Где взять учебную платформу

Официальная бесплатная [учебная платформа «1С:Предприятие 8.3» для Linux x64](https://online.1c.ru/catalog/free/28766016/). Дистрибутив выдаётся после заполнения анкеты и принятия лицензионного соглашения. Платформу **нельзя просто добавить в `nixpkgs` как свободную зависимость**. Установка и её системные зависимости выполняются отдельно от flake; лицензия или аппаратный ключ для учебной версии не нужны. Платформа должна поддерживать пакетный режим Конфигуратора.

## Как настроить GitHub CI с настоящей проверкой `.dt`

1. На собственном **Linux x86_64** сервере/ПК установить учебную платформу 1С и убедиться, что исполняется **`1cv8t`**. Не подменять его `1cv8` из коммерческой версии.
2. Установить и зарегистрировать GitHub **self-hosted runner**, добавив метку `onec-training`. Такой runner должен принимать задания только из доверенной ветки `main`; workflow не выполняет эти задания для pull request.
3. В **Settings → Secrets and variables → Actions → Variables** задать `ONEC_TRAINING_CI` = `true`, а также `ONEC_TRAINING_BIN` = абсолютный путь до `1cv8t`, например `/opt/1cv8t/x86_64/8.3.27.1508/1cv8t` (фактический путь может отличаться). Если бинарник находится в `PATH`, переменную `ONEC_TRAINING_BIN` можно не задавать.
4. Положить итоговую выгрузку из Конфигуратора в **`artifacts/warehouse.dt`**; файл хранится через **Git LFS**. Перед коммитом выполнить `git lfs install`, затем `git add artifacts/warehouse.dt`.
5. Запушить в `main` или вручную запустить workflow через **Actions → 1C laboratory CI**.

**Без `ONEC_TRAINING_CI=true`** весь штатный CI проверяет только инструменты, **не выполняет** реальную проверку базы. При включённом полном CI отсутствие `.dt`, учебной платформы, невозможность загрузки или ошибки конфигурации приводят к падению job, а не к фиктивному «успеху».

## Локальный запуск

```bash
nix develop
nix flake check
# Указать установленную учебную платформу (если не найдена автоматически):
export ONEC_TRAINING_BIN=/path/to/1cv8t
nix run .#validate-dt -- artifacts/warehouse.dt
```

`ONEC_TIMEOUT_SEC` задаёт лимит времени (в секундах) **на каждый этап**. По умолчанию 900. В безголовом окружении используется `xvfb-run` из Nix. База и логи создаются только во временном каталоге и удаляются по завершении.

## Ограничения и безопасность

- Учебная 1С предназначена для учебных задач; у неё действуют лимиты, в том числе на число сеансов и объём данных. Нужен файловый вариант базы.
- Для CI **не используйте** реальные рабочие или содержащие персональные данные `.dt`: это полноценная резервная копия информационной базы. Git LFS **не шифрует** содержимое.
- Не запускайте сторонние pull request на публичном self-hosted runner. Для проверки `.dt` достаточно доверенного `main`.
- При неудаче скрипт выдаёт журналы этапа, но не публикует архив базы. Если в журналах могут появляться персональные данные, не загружайте их как артефакты.
- Чтобы зафиксировать версии инструментов в точности, выполните `nix flake lock` и закоммитьте полученный `flake.lock`.
